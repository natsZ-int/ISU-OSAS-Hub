## 1. Purpose and method

A requirements specification is only as strong as its weakest link: a requirement that no design element answers, or a screen that no requirement justifies. This matrix makes both directions explicit so that a reviewer — or a panel — can pick any row and either find its design evidence or find a stated reason why there is none.

The matrix is generated, not maintained by hand. Requirement identifiers and their artifact links live in one registry (`_spec/requirements.csv`); the wireframe and mockup manifests record what was actually built; the UML source files record the diagram identifiers. The build reads all of them, so a matrix row cannot cite an artifact that does not exist.

### 1.1 Identifier scheme

| --- | --- | --- | --- |

| `ARCH-` | Architecture diagram | `ARCH-01` | 2 diagrams |
| `GAP-` | Implementation gap recorded during the audit | `GAP-03` | 12 gaps |

### 1.2 Status vocabulary

| Status | Meaning | Count |
| --- | --- | --- |
| Implemented | The delivered code performs the behaviour and the requirement is satisfied. | 146 |
| Partial | The behaviour exists but a stated part of the requirement does not. | 1 |
| Proposed | The behaviour is specified but not built; recorded so that it is not mistaken for delivered work. | 6 |

### 1.3 Verification method

| Method | Meaning | Applied to |
| --- | --- | --- |
| Demonstration | A reviewer can see the behaviour in a screen and its mockup. | Functional requirements with a design artifact |
| Inspection | The property is verified by reading code, routes or configuration. | Rules with no interface, and the usability, accessibility, maintainability, compatibility and portability requirements |
| Test | The property is verified by executing the system under load or attack. | Performance, reliability, security and data-integrity requirements |
| Not implemented | The requirement is proposed, so no method can be applied yet. | Proposed functional requirements |

The method is a statement about how the requirement should be checked, not a claim that it has been checked. Results belong in the test record, not in this matrix.

## 6. Maintenance

### 6.1 Procedure

1. Add or change the requirement in `_spec/requirements.csv`. The `wireframe`, `mockup` and `uml` columns are the trace links; leave a column empty when no artifact exists rather than inventing one.
2. If the change adds a screen, add it to the matching `wf_pages_*.py` module and rebuild the wireframes and mockups. The mockup builder derives each mockup's base screen from the requirement trace, so an inconsistent link fails the build.
3. Rebuild the SRS, the UML document, the wireframe document, the mockup document and this matrix. Each builder reads the registry, so no document holds a private copy of the links.

### 6.2 Guards

| Guard | Where | What it prevents |
| --- | --- | --- |
| Base screen must be in the mockup's own trace | `build_mockups.py` | A mockup that illustrates the wrong requirement. |
| Identifier set must be exactly MK-01 to MK-46 | `build_mockups.py` | A dropped or duplicated mockup. |
| Page counts must match the role group registry | `build_wireframes.py` | A dropped screen. |
| Diagram count must match the requested seven types | `build_uml.py` | A missing diagram type. |
| Requirement count and ID uniqueness | `build_srs.py` | A duplicated or dropped requirement. |

### 6.3 Confirmation needed
